## Platform

web

## Users

- **Primary: the owner / delivery lead** (the person who commissioned Odin). Opens it daily to answer one question first: *where is every deployment right now, and what is stuck?* Self-described "visual" — wants to see state, not read it. Then drills into one customer's rollout.
- **Delivery / project managers (Member role):** run each rollout day to day — move stages, tick tasks, upload deliverables, write status notes.
- **Sales / account managers (Contributor role):** create a project from a customer PO, watch progress, comment; never move a delivery stage.
- **Viewers:** read-only staff.
- **External participants (contractors, resellers, customer contacts):** invited to a project by email (only from allowed partner domains, if the admin set any), sign in with a one-time link (no password; opening it shows a Continue button so mail scanners can't spend it; lifetime set by the admin), see only the projects they are on, read and comment, tick tasks tagged to them. A customer contact may also approve or decline each stage change when the project asks for it.
- **Customers / vendors via the older per-project guest links** (view-and-comment, or advance one step): still live until invited accounts replace them.

## Product Purpose

Odin tracks the delivery lifecycle of every cybersecurity product and service the company sells — from purchase order through scoping, kickoff, deployment, tuning/UAT and hypercare to closed — for a security company running many rollouts in parallel. Success: nothing stalls unnoticed; the team, the customer and the vendor all see the same state of a rollout; the audit trail proves who did what.

Deliberately **not** a billing or commercial tool: invoices, payments and margins were removed and live elsewhere.

## Positioning

One shared pipeline for internal team, customer and vendor, with **stage SLAs measured from history** (time-in-stage reconstructed from status notes, targets set by hand or from measured averages), **per-party guest links** with different powers, and an **append-only audit trail** built for ISO 27001 / SOC 2 evidence. Generic project tools do not know what a security-product rollout is; Odin's stages, gates and parties are that rollout.

## Operating Context

- Internal Docker deployment on Proxmox, published through Cloudflare Tunnel + Access (MFA via Entra ID); guest links bypass Access.
- A rollout is created from a **client PO document** (required). Each has a client, vendor, product, delivery mode (Distribution/MSSP or Outsourced), owner, target end date, tasks with assignees and due dates, uploaded deliverables, status notes (some guest-visible), and two guest links.
- Stages are configurable per install; default lifecycle: PO Received → Scoping → Kickoff → Deployment → Tuning/UAT → Hypercare → Closed. The last stage is terminal everywhere.
- Alerts: overdue (past target end), due soon, stage-SLA breach, stale (untouched). Board banner shows them; a daily digest goes to admins; Teams/email via Microsoft 365 when connected.
- Rituals: daily glance at the portfolio; moving a card when a milestone lands; sending a guest link to a customer/vendor; quarterly access review from the users export; nightly backup.
- Scale: dozens to a few hundred active rollouts; a team of roughly 20–50.

## Capabilities and Constraints

- Stack: Flask + SQLite JSON API; React + TypeScript + shadcn/ui front end (Vite, Tailwind 4), ported page by page from Jinja (strangler). Every signed-in page is React; only the public guest pages, the login fallback form and the error page remain Jinja.
- Roles/permissions matrix (Admin, Member, Contributor, Viewer, External) enforced server-side; the UI must reflect them (Viewers and Externals see, never move). Per project, every participant also has a project role (Project manager = owner, Sales, Coordinator, Contractor, Reseller, Customer), and it binds staff too: only the Project manager moves stages, edits the project, its stage list, team, report and guest links; a Coordinator runs tasks and documents; everyone else on or off the project reads, comments, and ticks tasks tagged to them; a Customer contact approves stage changes. Admins bypass the project role.
- Every project owns its stage list: copied from a template in Settings at creation, then editable per project (add, rename, reorder, delete, SLAs). There is no shared stage header; each row carries its stage by name.
- Tasks belong to a stage of their project and are worked from the flow screen: add with an assignee from the project team, tick, delete. The person a task is tagged to may tick it whatever their role.
- **Plan and baseline** (30 Sep 2026): planned start/end per stage on the project page (Plan panel), with "fill the gaps from SLAs" and cascading moves. The first save freezes the plan as the baseline; every later move is logged with its reason, and re-baselining needs one. The forecast chains done stages (actual dates), the current stage (at least its planned length, never before today) and the rest (plan length, else SLA, else `default_stage_days`). Stage lengths, SLAs and time in a stage count **working days** (the working week minus the public holidays in Settings → General; `count_working_days` switches back to calendar days), while gaps between dates (slip, days late, days to target) stay calendar days; no digest or reminders go out on a holiday. Health is red / amber / green with its reasons and a confidence word; the thresholds are policies (`rag_amber_days`, `rag_red_days`); open blockers turn a rollout red, high-impact risks amber.
- **RAID register**: risks, issues, decisions and blockers per rollout, with owner (notified), due date, stage, impact/likelihood, resolution, and a "show in the customer's report" flag.
- **Rollout report** (`/projects/<id>/report`, 30 Sep 2026): one page and one PDF in two cuts. Internal: health and reasons, forecast vs target and baseline, Gantt (plan, actual, forecast, baseline), stage table with slip, what's next, the whole RAID register, work by stage with a burn-up, people, history (dwell vs SLA, approvals, plan changes, notes, documents). Customer copy: no baseline, slip, reasons, people or internal notes; only customer-marked RAID items and notes; plus "what we need from you" (pending approval, customer tasks, the PM's asks). The words (summary, next steps, asks) are drafted from the numbers and edited by the PM; "Save as version" freezes data and words as a numbered snapshot. Partners and customers see saved versions only, cut to the customer copy. Old plain-text versions still read.
- **Dashboard customisation** (30 Sep 2026): no edit mode; every widget has its own ⋯ menu (settings, width, earlier/later, remove), each change saves at once with an Undo; "Add widget" and a layout menu (admin: save as workspace default; reset). Rows never leave a gap: widgets pack in order, a row with room pulls up the next widget that fits and stretches its last one, for three, two or one columns.
- **Last seen and time on Odin**: active minutes are counted while Odin is open, visible and in use (a ping a minute, idle after `activity_idle_minutes`, at most one minute per 50 s); People shows last seen; a person's page shows today / 7 / 30 days and a 30-day strip to the roles in `activity_roles` (default Admins and Members); Settings → Sign-up & activity can switch it off (`activity_tracking`: nothing counted, panels gone, last seen = last sign-in); everyone sees their own on the Account page, with a note on what is measured.
- **Sign-up links**: admins make links (who for, role Member/Contributor/Viewer, optional project and project role, days (default `signup_days`), uses; revocable one by one or all at once; `signup_enabled` off stops every link and the making of new ones). A new colleague fills /join/<token> (name, work email within `signup_domains`, username, password, email or Teams) and waits as a pending account; admins are notified and approve on the Users page, which activates them and adds them to the project. Everyone picks email or Teams on the Account page (Teams delivered once Microsoft 365 is connected).
- **Document templates** (Settings → Documents): templates for the rollout report, the portfolio report and the sign-off — title, accent, our logo, an optional customer co-brand logo, a company line, a footer, sections on/off and in order, and text blocks with placeholders ({client}, {project}, {company}, {pm}, {po}, {stage}, {target}, {forecast}, {date}); one default per kind; the writer picks another per document; a preview renders the unsaved template on the newest project. Issued documents keep their template (a sign-off inside its fingerprint; a saved report version in its snapshot).
- **Scope and sign-off** (30 Sep 2026, the last phase of every rollout): the agreed scope is a list on the project page (Scope and sign-off panel), recorded while scoping and marked delivered / partly delivered / descoped at the end (the last two need a reason). A **Sign-off** stage sits before the terminal stage in every list (added to existing templates and open projects once; new stages are inserted before it), and the terminal stage cannot be reached until the sign-off is complete while `signoff_required` is on. The sign-off page (`/projects/<id>/signoff`) drafts the document — the scope item by item, or, with no scope, what was delivered from the stages and deliverables; outstanding items; handover and support terms (policy `signoff_terms`); the acceptance statement (policy `signoff_statement`) — and the project manager edits and sends it to a Customer or Reseller contact on the project, naming who countersigns for us. Sending freezes the version as canonical JSON with a SHA-256 fingerprint. The signatory opens it from the email's one-time sign-in link, reviews, and signs (drawn or typed, with name, title and an accept box) or sends it back with comments, which become an open customer-visible issue; then we countersign. The PDF certificate carries both signatures and the signing record (fingerprint, integrity check, who, when, from where — IPs for staff only). Fallbacks: upload a signed paper copy against an open version (filed under the Sign-off document category), or an admin waives it with a written reason. Every step is audited and notified; the signed PDF is mailed to both sides when mail is on.
- **Portfolio report** (`/reports/all`, PDF at `/reports/all.pdf`): health mix, late against target, behind baseline, open blockers, finishing in 30 days, a roadmap bar per rollout (start to forecast, baseline finish and target marked, worst health first), the slippage league, blockers and high-impact risks, and every rollout with its latest report. Partners and customers get the customer cut and no PDF.
- Notifications: a stage change emails every participant with an address (actor excluded), plus the owner and Teams. The project manager is also emailed when anyone else adds a note, finishes a task or uploads a document on their project; an approval decision reaches every participant. Every mail links to the project, an external account through a fresh one-time sign-in link. The project page also shows an Activity feed (the audit trail's own rows for that project, staff only) for people who do not read their email. Every notification also lands in the header bell (unread count, mark read, click opens the rollout) whether or not mail is connected; each user chooses by kind which ones also come by email (stage changes, approval decisions, activity on projects they manage, tasks assigned, mentions). A note can mention a team member as "@Full Name", "@username" or a unique "@First"; only people on the project can be mentioned. Nobody is told about their own action, and nobody gets the same event twice. Staff who forget their password request a one-time, 30-minute reset link from the sign-in page (the reply never says whether the address exists; a reset signs the account out everywhere). Each morning the daily script reminds every assignee of their tasks due today or overdue, in one summary. Since 1.3.0: new alerts reach the bell of the owner and the staff on the project (email per alert type), the daily digest goes to Admins and to each project manager for their own rollouts, approval requests are their own kind, people added to a project or made its manager are told, and the vendor link moves stages through the normal path (approval, history, the team told). Optional per project: the customer contact is asked to approve each stage change; the stage still moves, the decision is recorded, noted and audited.
- Guest pages are public-internet surfaces: no internal navigation, no internal notes, no PO number on the vendor link, author name required on every write.
- Drag-and-drop stage changes exist and are audited; vendor may advance one step only, never to terminal. The person who moved a stage can undo it for five minutes while it is still the latest move; the undo is audited and the team is told.
- All stored timestamps are UTC; rendered in the reader's zone.
- **Staff sign in with Microsoft** (Entra ID, one tenant, its own app registration). Microsoft proves identity; Odin decides the role. A colleague unknown to Odin waits for an admin to approve them with a role. Admins can require Microsoft for all staff; accounts they flag keep an emergency password form at /login/password, every use audited and announced to admins.
- **System map & changes** (Settings → Compliance, admins): the Odin System Map inside the app — architecture, lifecycle, notifications, permissions, ways in, code structure, tests, deployment, the loophole register — and a change log of every version, grouped by area, with the changes not yet released under the next version. Generated from the repository and shipped with each release, so it always describes the code the server runs.
- **Hardening in 1.3.0**: signing out ends that session server-side (a copied cookie stops working); Microsoft 365 tokens and client secrets are sealed at rest; access logs redact secret links; a failed restore test prunes no backup anywhere; settings routes follow the permission matrix; API token reads are audited daily; email failures while email is on reach the admins' bell.
- **Two-step sign-in** (1 Oct 2026) for password accounts: an authenticator-app code (TOTP) after the password, or one of ten single-use recovery codes. Anyone turns it on from the Account page (QR code or typed key, then a code; recovery codes shown once, downloadable); turning it off or making new codes needs the password and a code. The admin may require it for admins or everyone (`mfa_required`); someone who must and has not set it up is kept on the Account page until they do. Admins reset it for a lost phone (Users page; their sessions end). Microsoft sign-in keeps Microsoft's own check; partners' email links are unchanged. Secrets are sealed with a key derived from SECRET_KEY; codes work once.
- **My work** (`/my-work`): headline numbers (open, overdue, done this week, my rollouts), a fortnight of what got done, tasks grouped by urgency — overdue, today, this week, later, undated — ticked off in place, and the rollouts the person is on with their role and state.
- **People** (`/people`, staff only): a card for everyone internal on active work (rollouts, open, late, done in 30 days). A person's page shows their KPIs (incl. on-time rate), contribution per week, active rollouts, pending and upcoming tasks, what they did recently, and **Notify** — a note that lands in their bell and inbox (`nudge` notification kind, audited), optionally about one rollout.
- **Flow views** (`/board?view=`): the rollout list, a **Calendar** (a month of task due dates, rollout target dates, stage moves and customer decisions, with active rollouts as bars across their days; click anything to open it) and **Kibana** (Elastic dashboards an admin lists under Settings → Integrations, framed inside Odin — staff only; an address with `{project}`, `{client}` or `{po}` is drawn for one rollout at a time, the flow's selected one or a picker's).
- **Dashboard** (`/dashboard`, the home page — sign-in and the logo land there unless a person picks the flow on their Account page; partners always get the flow): live — the page polls a version number every 15 s and on focus and reloads when anything changed; a tile opens the rollouts behind its number; every widget expands to a full-size chart with its data as a table; chart type is a per-widget setting; **custom metrics** (rollouts by stage / client / state / owner / mode, tasks by person, tasks per day — as a number, bars, a pie or a list) can be added any number of times; eleven built-in widgets on a grid — headline numbers with week-over-week deltas and 14-day trends (from a nightly snapshot), the portfolio timeline with teams, portfolio progress, schedule (due tasks and approvals waiting), tasks completed, team load, rollouts per stage, recent activity, open alerts, my work, cycle time. An admin arranges the workspace default on the page itself; each person can reorder, resize, hide and tune their own copy and reset to the default. Every number is one the flow, the alerts, the analytics or the weekly report already compute.
- **Weekly report** (Settings → Reports): emailed on the chosen days to staff in the chosen roles plus extra addresses — needs attention first, stages moved this week, due in the next 7 days, rollouts per stage — optionally with the portfolio report and each active project's latest saved report as PDFs, and a summary to Teams (channel and/or a Workflows webhook, which also carries stage changes and decisions).
- **Audit retention** (Settings → Retention): 1–7 years or forever (default 3); older rows are archived nightly to a CSV (with a checksum, included in backups) before removal, and the removal itself is audited. The trail stays append-only for every account. The same page sets how long read notifications (`notifications_keep_days`, default 90; unread ones stay) and time on Odin (`activity_keep_days`, default 400) are kept.
- **Read-only API tokens** (Settings → API tokens): named, 30/90/365 days, shown once, revocable, last use shown; /api/v1 reads projects, stages, tasks and saved reports.
- **Backups** run on the schedule set in Settings (scheduler service, workspace time zone): database snapshot + documents + pictures + manifest, restore-tested (integrity check, every document present), copied to OneDrive, a SharePoint site folder and/or a mounted network share, pruned by daily/weekly/monthly retention locally and at each destination; every run and its restore-test result is listed in Settings → Backups.
- Admin settings are grouped by area (General, Sign-in & security, People incl. Sign-up & activity, Rollouts & workflow, Notifications, Integrations, Backups, Audit). Workspace policy an admin controls: company name, time zone, date format, working week and public holidays, new-user theme/accent, session idle and maximum length, password minimum, two-step sign-in requirement, sign-in attempt limit, upload size and types, undo window, default stage template and customer-approval default. Every change is validated against its limits and audited.
- Terminology (12 Oct 2026, the user's call): the UI says **rollout** wherever a person reads about the work (nav "Rollouts", "Open rollout", "the rollout can now close", emails and alerts); **project** stays only for the record and its form (New / Edit / Duplicate / Create / Delete project, "Project name", the project form), for the "Project manager" role, and in the brand tagline "Every project. On watch." URLs, API fields and template tokens (`{project}`) keep "project". Health reads in plan words only: On track / At risk / Off track, with the reason as detail. Also: *stage*; *task*; *deliverable*; *guest link* (customer / vendor); *SLA* = expected days in a stage.
- **Undecided:** whether time-on-axis (Gantt-style planned vs actual) becomes a first-class view or a detail-page section; how "gates" (required task/document before a stage change) are enforced — today they are not.

## Product Principles

1. **State before text.** The first screen shows where every rollout is and what is stuck, without reading a table.
2. **One pipeline, three audiences.** Team, customer and vendor look at the same flow with different powers; the UI never shows a party more than it may do.
3. **Time is a first-class fact.** How long a stage has taken, against its SLA, is always visible where the stage is.
4. **Every move is evidence.** Anything that changes a rollout is attributed, audited, and reversible where the product allows.
5. **Density serves scanning.** Hundreds of rollouts must stay legible; cap, cluster and summarise rather than list.
